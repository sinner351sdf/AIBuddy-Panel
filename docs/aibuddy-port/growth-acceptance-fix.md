# 成长任务接受确认修复（2026-10-16）

基于当前主项目及已合入的 3.0.7 未提交改动实施。本次不提交、不推送、不发布，不修改账号、凭证、排程或保留期。

## 证据与原因

启动任务记录 6489 的 15 个步骤中，10 项失败均为普通成长任务，提示“接受任务未确认生效，本轮停止”；同轮小程序任务成功。原始记录未保存逐次接受响应，不能据此判定每项上游请求的确切响应。

代码中可以确定的问题：

1. `task_execution::execute` 调用的 `billing::growth::accept_with_verify` 固定按小程序口径接受所有任务，却通过默认列表优先的查询确认状态。普通任务存在写入与回读口径不一致，小程序任务也可能读到普通列表中的旧副本。
2. 确认只做一次回读，回读失败、任务缺失和真正未登记均被折叠，随后再次 POST；未知的非空状态反而可能被视作成功。
3. 接受后的新任务进度没有返回执行器，后续动作仍使用接受前的快照。
4. 旧账号操作路径同时要求写响应严格包含 `accepted`，即使回读已确认仍会误报；领养路径还忽略确认失败。

## 改动

- 普通任务和小程序任务各自使用一致的列表、接受、进度回读口径。合并扫描时，小程序专属任务优先使用小程序列表，普通任务保留默认列表的状态。
- 两条执行路径共用有界确认流程：先查询；只有明确 `not_accepted` 才接受。每次写入后间隔 2 秒回读，最多 3 次；最后一次明确仍未接受，且写请求没有报错，才允许再接受一次。每轮最多两次接受请求。
- 超时、未知状态和缺失任务不会触发盲目重发；即使写响应丢失，也先回查是否已经登记。仅 `accepted`、`completed`、`claimed` 是明确登记状态。
- 返回确认后的完整快照，按最新进度补差额。已完成直接进入领奖，已领取直接结束；`completed` 即使缺少数值进度也不会再次执行动作。
- 停止信号在回读前后检查。仅领奖模式不接受、不执行任务。旧领养路径确认失败后停止。
- 执行记录保留具体失败阶段及 HTTP 状态；没有把历史失败记录改写为成功。
